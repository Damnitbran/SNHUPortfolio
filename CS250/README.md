# CS 250 - Software Development Lifecycle

This course covered the Agile and Scrum framework through a running project scenario (SNHU Travel), rotating through different Scrum roles each module. Included in this folder:
- Sprint Review and Retrospective document
- Agile presentation
- Coding assignments completed in Eclipse

## Reflection

**How do I interpret user needs and implement them into a program? How does creating "user stories" help with this?**

Most of the time users don't hand you a clean spec, they just describe a problem or something that's annoying them, and it's on you to translate that into something you can actually build. User stories help because they force you to frame things around who's using it and why, not just what the feature does. Writing "as an X, I want Y, so that Z" keeps the focus on the actual value instead of just checking a box. On the logistics inventory system I've been rebuilding, I didn't have any documentation to go off of, so I had to talk directly with the people using the old system to figure out what they actually needed day to day versus what they were used to working around. That's basically writing user stories informally, even without calling it that.

**How do I approach developing programs? What Agile processes do I hope to incorporate into my future development work?**

I've mostly worked solo, so my approach has always been pretty iterative by necessity. I build a piece, test it, see what breaks, and adjust instead of trying to plan out the entire system up front. This course put a name to a lot of what I was already doing without realizing it. Going forward I want to be more intentional about things like sprint reviews and retrospectives, even solo, just to force myself to stop and actually evaluate what's working instead of plowing ahead. Breaking work into smaller sprints instead of one long build is something I want to carry forward too, since it makes it a lot easier to catch problems early instead of finding out something's broken after months of work are already built on top of it.

**What does it mean to be a good team member in software development?**

Communication is the biggest one. It doesn't matter how good your code is if nobody else understands what you built or why. Being a good team member means writing things down, documenting decisions, and making sure the people around you aren't left guessing, especially since I've seen firsthand what happens when that doesn't happen. When I took over the logistics system, there was zero documentation left behind, so I had to rebuild it from scratch without knowing why past decisions were made. That experience stuck with me. Being a good team member also means being honest about problems early instead of hiding them, since that's what actually keeps a project moving instead of stalling out.
